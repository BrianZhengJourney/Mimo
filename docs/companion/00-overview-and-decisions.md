# 伴灵模式 2.0 — Shimeji 交互模型研究 & Mimo 架构计划

> 2026-07-18。研究对象:原版 Shimeji(Group Finity, ~2009)、Shimeji-ee(Kilkakon
> 维护线,affordance/hotspot 扩展)、Shimeji-Desktop(现代 Java fork,本文引用的
> 主要源码)、libshijima(C++ 洁净室重实现)。
> 目标:把 Mimo 的伴灵交互从"角落里的状态指示器"升级成一个 robust 的、
> 有物理手感的桌面生命体 —— 同时保留 Mimo 独有的灵魂:**它知道你在专注,
> 专注时它不打扰你**。

---

## TL;DR

- Shimeji 手感好的本质不是动画多,而是 **五件事**:数据驱动的两层行为系统
  (Behavior 选择 × Action 执行)、只在坠落/抛掷用真物理、拖拽的阻尼弹簧
  "拎起来会晃"、把窗口边缘当地形、以及一条冷酷统一的打断规则(抓起/落地/
  地面消失永远立刻接管)。
- Mimo 现状:交互 = 点击 + 拖 panel + 右键,唯一自主移动是脚本化 victory walk。
  没有物理、没有行为数据模型、没有窗口几何感知;动画全是 CSS keyframes,
  运动与渲染耦合在一个 560×320 的角落 panel 里。
- 计划:把"伴灵本体"从 overlay panel 里拆出来,**改为原生 CALayer 渲染**
  (每显示器一个透明全屏层,`CVDisplayLink` 单一时钟),Swift 里跑
  environment + physics + behavior 引擎(行为包用 JSON + 条件表达式,
  机制照抄 Shimeji 的精华)。WKWebView 退居 HUD/journal,不再承载伴灵。
  Mimo 的 focus 状态机不再直接驱动动画,而是作为**情绪层调制行为权重**
  —— 这是 Shimeji 没有的、Mimo 独有的一层。
- 分五阶段:P0 原生宿主+物理手感 → P1 行为系统数据化 → P2 多屏漫游 →
  P3 资源包动作分级(生成 pipeline 扩展到 N 帧行为包)→ P4 窗口地形 +
  多实例/热点/声音。

> **修订记录(2026-07-18 晚)**:本文档初稿完成后,三项架构取舍已拍板,
> 与初稿结论有两处实质冲突,相关章节已按新决策重写。见 [§0 决策记录](#0-决策记录)。
> 初稿中"专注时安静"的产品原则(§3.1)保留不变 —— 它仍是本计划的核心立场。

## 0. 决策记录

### D1:渲染宿主 → **原生 CALayer**(推翻初稿的"WebView 纯渲染")

**决定**:伴灵改为原生 AppKit/CALayer 渲染,每个 `NSScreen` 一个透明全屏
overlay 层,所有伴灵在同一层树内合成,`CVDisplayLink` 驱动单一时钟。
WKWebView 退居 HUD/journal 窗口,**不再承载伴灵本体**。

**理由**:四个瓶颈只有原生能解 —— 多实例合成、精确 alpha 命中测试、
per-display HiDPI、ProMotion 撕裂。而且现状**已经**在两个互不同步的动画
时钟上出问题(`victoryWalk()` 期间 CSS 编译器 + 60Hz `Timer`),初稿的
"每 tick postPose 过桥"方案等于把这个已知最脆的地方放大到每一帧。

**代价**:重写渲染层;`overlay.html` 约 30 个 CSS keyframes 要迁移;
像素 lane(字符串网格 → SVG rect)需要一条新的 CALayer 渲染路径
(建议预渲染成 `CGImage` 缓存,而非每帧重建图元)。

**被拒绝的替代**:*全屏透明 WebView + canvas 引擎*(改动小但常驻耗电、
alpha 命中要 JS 回传、多屏麻烦);*混合 = 初稿 §4.2 方案*(保留美术管线,
但双时钟同步是已知痛点)。

### D2:动画帧来源 → **扩展生成管线到 N 帧行为包**(推翻初稿 Q3 的建议)

**决定**:改 prompt + `character_sheet.swift` + manifest,生成成套动作表。
初稿建议的"T0 程序化为默认、运动 sheet 作可选付费项"降级为**增强层**而非
主方案。

**理由**:最接近 Shimeji 手感。**用户不追求养很多伴灵,更在意少数几只
高质量的** —— 一次性生成成本因此可接受,且运行时零成本。

**配套决定(2026-07-18 追加)**:**生成后端抽象成可替换的 provider 接口**,
不锁死 gpt-image。见 §4.8(接口)、§4.9(provider 对比)、§4.10(验收标准)。

**已知风险(必须主动管理)**:帧间身份漂移是图像模型的硬伤;成本;部分失败。
三条缓解的核心分别是:**一次调用出整张图集**(模型在同一张图内保持一致性
远好于跨调用)、**T0–T3 动作分级**(可用伴灵只需 +1 次调用)、
**`generation_draft.swift` 从锦上添花升为必需路径**。

> ⚠️ **两个流行前提在本轮核查中被推翻,直接影响本决策的执行方式:**
>
> 1. **「固定 seed 保证一致性」不可行 —— OpenAI 与 Google 的图像模型
>    都没有 seed 参数**(已在多个官方页面由"参数列表中不存在"确认)。
>    唯一已核实带确定性 seed 的是 Vertex AI Imagen(且要求关水印),
>    属另一个模型家族。
>    **推论:一致性只能"生成后验证并修复",不能"事前保证"。**
>    这把 §4.10 的度量循环从可选项提升为**架构承重件**。
> 2. **「nano banana 在角色一致性上更好」未能证实。** 该印象似乎源自
>    2025 年 Gemini 2.5 Flash Image 时期。截至 2026-07 我能核实的唯一
>    公开盲测榜上,gpt-image-2 反而领先最好的 Gemini 条目约 77 Elo ——
>    但那个榜测的是通用图像编辑偏好,**不是**跨帧身份保持,
>    而后者我没有找到任何隔离测量的基准。**两个方向的证据都不足。**
>    **推论:provider 之争用 §4.10 的评分函数在我们自己的角色上跑 A/B 解决,
>    不凭口碑。这也是 provider 接口的首要理由。**

**明确记录**:程序化变换层(skew / squash-stretch / 镜像 / bob)**仍然要做**
—— 它让 T0-only 的旧伴灵不至于是死的,也让 T1 的 9 帧看起来像 20 帧。
**这不是妥协,这是 Shimeji 也在做的事**:它的 `Dragged` 只有 7 张手绘图,
靠 `footDx` 弹簧撑起整个摆动感。

### D3:窗口感知 → **分阶段,先屏幕边缘**(初稿放在 P2,现推后到 P4)

**决定**:P1 之前只做屏幕/工作区边界的重力、投掷、贴边;窗口攀爬推到 P4。

**理由**:风险最低,早期就能拿到 80% 手感;且窗口枚举的权限成本尚未实测
(见 §4.5 的核实标注)。

**架构保障(必须在早期就做对)**:`SurfaceResolver` 的接口从一开始就按
**"表面集合"**设计,而不是"屏幕边 + 特判窗口边"。P4 加窗口边界时只需
**往数组里塞更多 `Surface`,物理层与行为层零改动**。这是这个决策能低成本
兑现的前提。
